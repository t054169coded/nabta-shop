# Nabta / نبتة

An online shop for indoor plants, built with plain HTML, CSS and JavaScript —
no frameworks, no libraries, no build step.

The idea: **every plant arrives young and small, and you can see how big it
will get before you buy it.** Hover a plant (or tap it, or press Enter on it)
and it grows to full height beside a 170 cm person, with a measuring rule up
the side of the frame.

---

## Running it

**Double-click `index.html`.** That works — the scripts are plain classic
scripts, not ES modules, precisely so the site runs straight off the disk.

To see it the way it would really be served (and to have it load
`data/products.json` through `fetch`, which the `file://` protocol blocks):

```bash
python3 -m http.server 8123
```

Then open <http://localhost:8123>. When `fetch` is unavailable the catalogue
falls back to `data/products.js`, an exact mirror of the JSON generated by
`tools/mirror.py`. Both routes give the same site.

## How the growth animation works

The plants are not photographs being scaled up — each one is drawn as SVG so
three things can move at once, which is what makes it read as *growing*
rather than *zooming*:

1. **`.foliage`** — the whole plant scales up from the soil line
   (`transform-origin: 0 0`, so it grows out of the pot rather than from its
   own middle).
2. **`.lf`** — every leaf unfurls on a stagger, and the leaves marked
   `.lf--mature` do not exist at all until the plant grows, then fade in.
3. **`.st`** — stems and vines draw themselves on from the base outward, using
   `pathLength="100"` and an animated `stroke-dashoffset`.

Meanwhile JavaScript counts the height readout up with
`requestAnimationFrame`, and the person and the measuring rule fade in behind.

Each leaf is wrapped twice on purpose: the outer `<g>` holds the SVG
`transform` **attribute** (where the leaf sits, how it is angled) and the inner
`<g class="lf">` is the one CSS animates. Putting both on one element would let
the CSS transform wipe out the placement.

Anyone whose system asks for reduced motion gets the grown state immediately,
with no animation and no counting.

### Making six plants look like one photo shoot

Every plant is drawn in the same "studio": the same 440 × 640 frame, the same
wall gradient, the same window beam, the same floor line and the same pot.
That shared frame is what makes a fiddle fig and an olive tree look like they
were photographed on the same afternoon.

The pothos is the one exception in composition — it hangs from a wall shelf,
because a trailing plant needs somewhere to trail from — but the wall, floor,
light and pot are identical.

## The care calendar

Watering is counted forward from `boughtOn`, the date the plant was bought.
Placing an order sets that date to today automatically; you can also add a
plant by hand with any past date.

- **Watering** restarts from the last time you actually marked it watered.
- **Rotating** and **feeding** run on fixed intervals from the purchase date.
- **Kuwait summer** (June–August) shortens every watering gap by 30%, decided
  per step — so a schedule that runs into June tightens up on its own.
- Overdue tasks are looked up two weeks back so they cannot quietly vanish.
- **Export** builds a `.ics` calendar file in JavaScript with `Blob` and
  `URL.createObjectURL`, and hands it to the browser as a download.

## Checkout, and why there is no card form

`checkout.html` collects a Kuwaiti address — governorate, area, block, street,
building — because that is how addresses work here; there is no postcode, so
none is asked for. Phone is validated as a Kuwaiti mobile: eight digits
starting 5, 6 or 9, with `+965` shown inside the field so only the digits get
typed.

Payment offers **cash on delivery** and **KNET card on delivery**. Both are
paid at the door, which is exactly why they work in a site with no server.
"Pay online by KNET or card" is shown but disabled, with the reason on the
page.

**No card number is asked for anywhere on this site, and that is deliberate.**
A front-end-only shop cannot take a payment: there is no server to receive it.
A form that *looked* like it took cards would invite a real card number into a
page with no encryption and no PCI compliance. Real shops do not collect cards
on their own form either — the payment provider hosts that step so the details
never touch the shop's code. For Kuwait that means MyFatoorah or Tap Payments,
both of which handle KNET, and both of which need a server.

Placing an order writes an order record, starts each plant's watering schedule
from that day, empties the cart, and sends you to the confirmation page. The
order copies each plant's name and unit price at the time of purchase, so a
later price change cannot rewrite an old receipt.

## Connected to Supabase

The catalogue, accounts, cart, plants and orders live in a Postgres database
(see [supabase/README.md](supabase/README.md) for the schema). The wiring is in
`js/supabase.js`.

**How it fits a site built on synchronous storage.** The pages read state
synchronously — `cart.items`, `owned.all` — and Supabase is asynchronous.
Rather than rewrite every call site, localStorage stays the working copy the
UI reads, and `js/supabase.js` keeps it in step:

- **on page load or sign-in** it pulls from the database, overwrites the local
  copy, and fires the change events the pages already listen to, so every view
  re-renders itself
- **on every `write()`** — the single choke point in `js/app.js` — it schedules
  a debounced push of that key

So the site still works with no network, and still works opened straight off
the disk. It just forgets between devices, exactly as it did before.

**The catalogue comes from the database first**, then `data/products.json`,
then the mirror — each fallback a normal outcome, not an error. The remote
attempt gives up after 2.5 seconds so a slow database never leaves you
staring at placeholders.

**Accounts are real.** Email and password go to Supabase Auth, which hashes
the password on its own servers; no file here and no table in the schema ever
holds one. This project has email confirmation switched on, so signing up
sends a link that has to be clicked before the first sign-in.

When Supabase cannot be reached — `file://`, or the CDN blocked — the sign-in
page falls back to its original local-only behaviour and *says so on the
page*, so it is never misleading about which one you got.

**One rough edge, stated plainly:** cart, wishlist and plants are synced by
replacing all of that user's rows. It is simple and can never drift from what
the browser shows, but it is not crash-safe — a network drop between the
delete and the insert leaves those rows empty in the database until the next
successful push. localStorage still holds the truth locally, so nothing is
actually lost, but a production shop would diff instead.

## Sign-in page

Email is checked with a regular expression, country is a `datalist` of 173
countries, and the chosen country drives the delivery estimate shown right
under it (Kuwait 1–2 days and free over 20 KWD, the GCC 3–5 days, elsewhere
not yet). Errors appear inline under the offending field, never in an
`alert()`.

**This is a front-end demo.** The "session" is a flag in `localStorage`,
nothing is sent anywhere, and no real password should ever be typed into it.
Real authentication has to happen on a server.

## Techniques used, for reference

**HTML** — semantic sectioning, `<fieldset>`/`<legend>`, `<datalist>`,
`<details>`/`<summary>`, `<output>`, `data-*` attributes, ARIA labels and
`aria-live` regions, `loading="lazy"`.

**CSS** — custom properties for the whole palette, Grid, Flexbox, logical
properties throughout (which is what makes RTL work), `aspect-ratio`,
`color-mix()`, `backdrop-filter`, `position: sticky`, transitions, keyframes,
SVG-targeted rules, `:focus-visible`, `prefers-reduced-motion`,
`prefers-color-scheme`, media queries at 1080 / 900 / 640 px.

**JavaScript** — `async`/`await` with `fetch` and a graceful fallback,
a `Cart` class,
`map`/`filter`/`reduce`/`sort`/`find`/`flatMap`, destructuring, spread,
optional chaining, `??=`, template literals, event delegation, a debounced
search, `localStorage`, `URLSearchParams` + `history.replaceState`,
`IntersectionObserver`, `requestAnimationFrame`, regex validation, custom
events, `Blob` downloads, and date arithmetic that avoids UTC drift.

The scripts are loaded with `defer` in dependency order — `i18n`, the data,
`plants`, `app`, then the page's own file — rather than as ES modules, so the
project still opens by double-clicking. Each file keeps a single clear
responsibility.
